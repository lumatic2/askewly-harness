## 한 규칙 — 이해 vs 추측, 제3의 선택지는 없다

load-bearing 결정(바꾸면 하류를 다시 써야 하거나, 사용자가 취향을 가질 결정)마다 딱 두 상태만 인정한다:
- **이해했다** — 사용자가 말했거나, 그들의 목표·가치·제약 모델 + 도메인/레포 실측에서 유도된다. → 그대로 실현한다(파생 가능한 것은 재질문하지 않는다).
- **추측이다** — 이해 없이 고르면 "이 사용자를 이해하지 못한 사람의 합리적 기본값"이고, 그것도 여전히 추측이다. → 기본값으로 넘어가지 말고 아래 방법으로 닫는다.

추측이 살아남으면 나중에 재작업·엉뚱한 방향 구현·얇은 결과로 터진다. 예외는 **튜닝값**뿐 — 확정된 메커니즘 안의 설정값으로 사용자가 취향을 가질 이유가 없는 것(기본값 기록 + tunable 마킹, 묻지 않는다). "사용자가 이 값에 진짜 취향이 있나, 아니면 관례 기본값/나중에 조정할 값인가"가 판별 질문이다.

## 두 방법 — 지식이 어디 있느냐로 가른다

| 결정이… | 지식 보유자 | 방법 | 어떻게 |
|---|---|---|---|
| 도메인·행동·취향 | **사용자** | **EXTRACT (캐묻기)** | "X 상황이면 어떻게 돼야 하나"를 끝까지. 에이전트가 지어내지 않는다. **열린 질문 기본** — 선택지로 가두면 사용자의 모델을 에이전트의 모델로 덮는 역방향(선택지를 주더라도 "다른 그림 있음" 열린 항목 필수) |
| 기술 | **에이전트** | **PRESENT (제시)** | 캐낸 도메인 위에서 선택지+트레이드오프+추천, 사용자가 고른다 — 기존 논의 루프([선택지+추천+근거])가 이것 |

PRESENT 는 EXTRACT 에 의존한다 — 도메인을 이해하기 전에 낸 기술 선택지는 엉뚱한 문제를 푼다. 도메인 이해가 앞서고, 기술 결정은 그 위에서 제시한다.

## 사용자 모델을 만들며 대화한다

이해는 느낌이 아니라 대화 중 유지하는 **모델**이다: 목표(진짜 이루려는 것 — 기능 목록이 아님) · 가치/우선순위(반복해 돌아오는 말 — 세 번 말한 단어는 핵심 가치) · 제약(규모·마감·플랫폼·"그냥 개인 프로젝트") · 지금까지 준 도메인 사실. 결정마다 "모델이 이 결정을 근거 짓는가"를 대조한다 — 근거하면 안 묻고 실현, 모델이 침묵하면 그게 갭이다(침묵을 기본값으로 채우는 것이 곧 추측).

## 결정 표면 열거 → 소진

사용자는 load-bearing 결정의 일부만 말한다. 나머지를 끄집어내는 절차:

1. **엔티티 manifest** — 이 작업이 건드리는 엔티티·행위자·상태 보유자·외부 시스템을 나열한다. 이름 안 붙인 것은 훑지도 못한다. 닫기 전에 "안 이름 붙인 게 더 있나"를 한 번 묻는다.
2. **4렌즈 스캔** — 각 엔티티와 충돌 쌍에:
   - **구조**: cardinality·구성·정체성·관계 (X 하나에 Y 하나인가 여럿인가 — 이 렌즈를 건너뛰어 터진 실사례가 dryforge 에 기록돼 있다)
   - **행동**: 생애주기(생성→변화→종료)·동시성(공유 상태를 두 행위자가 동시에 만지면?)·엣지 처분. 개념 조합이 만드는 미언급 엣지도 훑는다("취소 가능" + "결제 붙음" → "취소 시 결제는?")
   - **기술**: 영속성·인터페이스/전달 형태·일관성 모델
   - **계약**: enum 값 집합·유일성 규칙·개념상 별개인 두 필드의 병합 여부
   렌즈는 **가속기이지 전수 목록이 아니다** — 안 맞는 결정이 나오면 이 도메인의 렌즈를 새로 이름 붙인다.
3. **과잉 질문 방화벽 — 열거는 전수, 질문은 최소.** 찾은 결정마다 고정 순서로 거른다:
   1. 사용자 모델이 근거한다(발화·유도·이미 고른 선택지) → **묻지 않고 실현**
   2. 확정 메커니즘 안의 튜닝값 → **기본값 + tunable 마킹, 묻지 않음**
   3. 둘 다 아님 = **assumed** → **그것만 질문** (도메인이면 EXTRACT, 기술이면 PRESENT)

## 종료 조건 — 스캔이지 느낌이 아니다

- **assumed 가 하나라도 남으면 결정 로그에 `status: resolved` 를 적을 수 없다.** 사용자가 "그 정도면 됐어"라고 해도 열거 표면에 assumed 가 남았으면 닫힌 게 아니다.
- **얇은 요청은 바를 낮추지 않는다 — 올린다.** 신호가 적을수록 더 묻고 더 캔다. 얇은 입력에서 얇은 계획을 내는 것이 이 절차가 막는 바로 그 실패다.
- 표면 열거는 **작업 메모리**다 — plan doc 에는 결정 로그의 *결론*만 남기고 열거 표·태그를 남기지 않는다(dryforge 도 spec 에 provenance 태그를 금지한다).
- **잘 묻기**: 빈손으로 던지지 않는다 — 도메인은 구체적 초안 제시 후 조정받고, 기술은 추천+트레이드오프 선행. 지렛대 큰 것부터, 관련 질문은 묶어서. "질문을 채워 성실해 보이기"는 금지지만, 그 금지는 잡담 질문에만 적용된다 — load-bearing 을 건너뛰는 핑계가 못 된다.
- **하류 검증자(fresh 계획 검증자)는 백스톱이지 안전망이 아니다.** 검증자가 잡을 것을 기대하고 최소 통과선으로 닫는 것은 reward-hacking 이다 — 검증자가 없다고 치고 소진한다.
